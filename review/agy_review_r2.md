## A. 1라운드 조치 검증

R1: 해결
확인: §5.3에서 문맥 상한을 40,000자에서 16,000자(UTF-8)로 축소 반영했고(`D15`), §6.3에서 stdin 주입 공급자(codex, claude)와 인자 전달 공급자(agy)의 프롬프트 전송 방식을 분리 규정했다. agy의 stdin 우회 불가 실측을 인정하고 가장 제약이 큰 agy에 맞춰 공통 16,000자 상한을 적용함으로써 동일 조건 교차검증 원칙(`INTENT.md` §5)을 온전히 보존했다.

R2: 해결
확인: §6.3의 공급자별 실행 파일 탐색 우선순위에서 위험한 `.cmd` 및 `.ps1` 폴백을 완전히 제거했다. 네이티브 `codex.exe` 탐색 실패 시 `node.exe` + `codex.js` 직접 실행으로 강등하고 이마저 실패 시 비활성화하도록 개정하여, Windows `%ComSpec%` 셸 메타문자 재해석 위험을 원천 제거했다.

R3: 해결
확인: §7.6에 HTML 주석 마커(`<!-- msg id=... round=... sender=... -->` 및 `<!-- /msg id=... -->`) 기반의 메시지 경계 규격을 신설했다. 내부 `<!-- /msg` 이스케이프 처리 및 불일치 시 `CORRUPT` 표시 후 나머지 정상 복원, 원자적 파일 교체(atomic replace) 정책을 명시하여 외부 라이브러리 없이(`D12`) 손실 없는 채팅 재개(SSOT)가 가능해졌다.

R4: 해결
확인: §7.5-1 "수렴자 실행 계약 (Consolidator)"을 신설했다. 수렴자의 비판정/분류 역할, 참여자 중 1인 지명 방식(해당 AI는 검토에서 제외), 1라운드 완전 합의 시 즉시 종료 및 최대 2라운드 종료 조건, 실패 처리 정책을 구체적으로 규정하여 Phase 3의 아키텍처 결손을 해소했다.

R5: 해결
확인: §7.7에 Java 600초 타임아웃 주체 일원화가 확정되었고, 비정상 자식 정리를 위한 `ProcessHandle.descendants().forEach(ProcessHandle::destroyForcibly)` 규약이 명시되었다. 열거-종료 간 경쟁 조건은 Java 표준 범위 내 재시도 루프 및 Windows 기본 유틸리티 `taskkill /PID <pid> /T /F` 보조 실행으로 Phase 1 구현 단계에서 충분히 통제 가능하므로 스펙 수준에서는 착수 가능 상태다.

R6: 해결
확인: §5.3 말미에 "Phase 3 예외" 조항을 신설하여 일반 대화의 16,000자 슬라이딩 윈도우와 Phase 3의 증거 보존 정책(최초 안건, 구조화 응답, 반론의 필수 보존)을 명시적으로 분리했다.

R7: 해결
확인: §5.2의 Phase 1 (MVP) 명령 목록에 `/cancel`, `/rooms`, `/open`을 정식 포함하도록 개정했다. 이로써 §7.9의 Phase 1 구현 범위 및 §7.10의 "`/cancel` 프로세스 종료", "종료 후 채팅방 재개" 완료 기준 간의 내부 불일치가 완전히 해소되었다.

R8: 해결
확인: §7.0에 `D18`을 신설하고 §7.8에 대상 워크스페이스 결정 규칙 7개 항을 명문화했다. 시작 옵션 `--workspace`, 방 메타데이터, 현재 디렉터리의 우선순위와 절대 경로 정규화, 세 공급자 동일 경로 전달, 디렉터리 변동 시 사용자 확인 절차가 구체적으로 확정되었다.

R9: 해결
확인: §7.5-1 신설 및 §5.3 Phase 3 예외 조항을 통해 라운드별 비대칭 문맥 구성의 요구사항과 상태 흐름이 문서상으로 정립되었다. `PromptContextBuilder`를 라운드 상태 인식형으로 확장하는 것은 단일 클래스 내부의 메서드 분기 구현으로 충분하며 클래스 구조 변경 없이 Phase 1에 무리 없이 착수 가능하다.

R10: 해결
확인: §7.2의 Codex 프로필 및 §7.6 저장 규약에서 임시 출력 파일 경로를 워크스페이스 외부인 `%USERPROFILE%\.multi-ai-cli\temp\<run-id>.md`로 명시 격리했다. 또한 라운드 종료 시 `try-finally` 파일 정리 및 부재 시 stdout/stderr 스트림 폴백 정책까지 완비되었다.

R11: 해결
확인: §6.3에 "콘솔 출력 인코딩을 별도로 맞춘다" 항목을 신설하여 `scripts/run.ps1`의 `chcp 65001` 및 `[Console]::OutputEncoding = UTF8` 설정, Java 실행 인자(`-Dfile.encoding=UTF-8` 등) 지정을 의무화했다. 한글 왕복 스모크 테스트도 파일과 콘솔 양쪽에서 검증하도록 규정되었다.

## B. 상대 단독 지적에 대한 입장

R5: 부분 동의
근거: Codex의 지적대로 `ProcessHandle.descendants()`는 특정 시점의 프로세스 스냅샷을 순회하므로 열거와 종료 사이에 분기된 자식이나 분리된 자식을 놓쳐 좀비가 발생할 이론적·실제적 가능성이 존재한다. 그러나 대상 프로세스가 상주형 서비스가 아닌 단발성 CLI라는 점, 그리고 외부 Java 의존성(`D12`)을 건드리지 않고도 Windows 내장 `taskkill.exe /PID <pid> /T /F`를 2단계 폴백으로 안전하게 호출할 수 있다는 점에서, 이는 프로세스 런처의 구현 방어선 강화로 해결할 수 있으며 Phase 1 착수를 막는 결함은 아니다.

R6: 동의
근거: Phase 3 구조화 수렴은 세 AI의 1라운드 독립 응답, 상호 반론, 최초 안건 전체를 대조하여 쟁점을 좁히는 절차다. 최근 대화만 남기는 슬라이딩 윈도우가 작동할 경우 수렴의 근거 데이터가 유실되므로, Phase 3 전용 문맥 보존 정책을 분리 규정한 Codex의 지적은 정확하다.

R7: 동의
근거: §5.2의 MVP 기능 목록과 §7.9, §7.10의 완료 기준(취소, 채팅방 재개)이 어긋나 있던 것은 명백한 스펙 내부 모순이었다. 완료 기준에 맞춰 `/cancel`, `/rooms`, `/open`을 Phase 1으로 일치시킨 정리는 구현 범위의 혼선을 깨끗이 제거했다.

R8: 동의
근거: 워크스페이스 경로가 명시적으로 고정되지 않으면 각 CLI가 서로 다른 디렉터리를 탐색하거나 잘못된 위치를 참조할 위험이 있다. 방 단위 고정 메타데이터와 `--workspace` 우선순위 규칙을 정립한 Codex의 지적은 다중 도구 오케스트레이션의 안정성을 확보하는 데 필수적이었다.
