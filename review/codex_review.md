# codex_review — multi_ai_cli 설계 검토

- 검토자: codex
- 모델: GPT-5 (Codex)
- 읽은 파일: `INTENT.md`, `SPEC.md`
- 판정: CONDITIONAL

## A. 의도 확인

이 프로젝트는 Claude·Codex·Gemini를 독립 참여자로 호출하고, 같은 라운드에서는 서로의 답을 숨겨 동조를 방지하는 Java CLI 애플리케이션이다. 핵심 목표는 단순 병렬 호출이 아니라 여러 모델의 답을 합의·이견·단독 지적·미해결로 분류하고, 최대 2라운드의 반론을 통해 사용자가 결정할 쟁점만 남기는 것이다. 공급자 세션이 아니라 애플리케이션의 채팅 기록을 공동 문맥의 SSOT로 사용하며, 응답과 오류의 출처를 항상 분리한다. Phase 1과 Phase 2는 이 구조화 수렴에 도달하기 위한 기반이다.

- 끝까지 모호했던 것: Phase 3에서 누가 분류·수렴을 수행하며, 어떤 조건으로 합의와 미해결을 판정하는지 명시되지 않았다. `prompts/consolidate.md`가 출력 형식은 제공하지만 실행 주체와 실패 처리 정책은 `SPEC.md`에 없다.
- 당연하다고 전제하지만 적혀 있지 않은 것: 임의 길이의 채팅 문맥을 각 CLI의 명령행 인자로 안전하게 전달할 수 있다는 전제와, Markdown transcript에서 임의의 AI 출력을 손실 없이 다시 구조화할 수 있다는 전제가 숨어 있다.

## B. 미해결 쟁점 Q1~Q6 판정

Q1: 동의  
근거: Java 17 표준 라이브러리만으로 공급자별 JSON을 안정적으로 처리하려면 파서를 직접 구현해야 하며, 이는 MVP 범위를 불필요하게 확대한다. Phase 1은 최종 텍스트만 필요하므로 Claude·agy의 기본 text 출력을 사용하는 것이 D12와 일치한다.

Q2: 조건부 동의  
근거: 공급자 공통 타임아웃을 Java에서 강제해야 부분 실패 정책과 취소 상태를 일관되게 기록할 수 있다. 다만 권장안의 “agy 타임아웃을 Java보다 짧게 두지 않는다”와 예시인 “agy 10분, Java 11분”은 서로 반대다.  
대안: Java의 사용자 관찰 타임아웃을 600초로 고정하고 agy 자체 타임아웃을 11분처럼 더 길게 설정해, Java 감시가 실패했을 때만 CLI 측 안전장치가 작동하게 한다.

Q3: 동의  
근거: `--tools ""`는 도구만 차단하지만 `--restricted`는 사용자·프로젝트 설정 상속도 차단한다. 세 공급자가 애플리케이션이 만든 동일 문맥에서 출발하려면 Claude에만 외부 설정이 주입되는 경로를 닫아야 한다.

Q4: 정보부족  
근거: 실제 소스 루트로 현재 디렉터리를 사용할지 별도 `multi_ai_cli` 디렉터리를 만들지, Git 저장소를 생성할지에 대한 사용자 결정이 없다. 이 두 값을 알아야 프로젝트 골격과 스크립트 경로를 확정할 수 있다.

Q5: 조건부 동의  
근거: `--restricted`는 설정 상속을 줄이지만 중첩 실행의 사용량, 부모 세션 종료, 프로세스 트리 혼동을 해결하지는 않는다. 실행 환경 감지는 완전하지 않을 수 있으므로 경고를 안전성 보장으로 취급해서는 안 된다.  
대안: 확인 가능한 부모 환경 표식이 있을 때 `/status`에 비차단 경고를 표시하고, 중첩 여부와 무관하게 자식 PID와 실행 ID를 애플리케이션이 독립 관리하도록 한다.

Q6: 정보부족  
근거: 모델 목록만으로 `gemini-3.1-pro-high`의 품질·지연·구독 한도·컨텍스트 크기가 주 용도에 적합한지 판단할 수 없다. 후보 모델의 실제 응답 품질과 지연 측정, 그리고 사용자가 정확도와 속도 중 무엇을 우선하는지 알아야 기본값을 정할 수 있다.

## C. 새로 발견한 문제

[critical] Codex `.cmd` 대체 경로가 사용자 프롬프트를 셸 명령으로 재해석할 수 있다  
위치: `SPEC.md` §6.3, §7.8  
문제: `ProcessBuilder`에 배열로 전달해도 `%ComSpec% /c` 이후의 인수는 `cmd.exe`가 다시 파싱한다. 따옴표와 `&`, `|`, `<`, `>` 등이 섞인 프롬프트는 손상되거나 Codex 샌드박스가 시작되기 전에 셸 명령으로 해석될 수 있어 “프롬프트를 셸 문자열에 연결하지 않는다”는 보안 경계가 성립하지 않는다.  
제안: `.cmd` 호출을 대체 경로에서 제거하고 네이티브 `codex.exe` 또는 `node.exe`와 Codex JS 진입점을 직접 실행한다. 안전한 직접 실행 경로를 찾지 못하면 `/status`에서 지원 불가로 표시한다.

[major] 문맥 크기 상한이 Windows 명령행 길이보다 클 수 있다  
위치: `SPEC.md` §5.3, §7.2  
문제: 약 40,000자의 문맥에 현재 요청과 실행 메타데이터까지 하나의 인자로 붙이면 Windows `CreateProcess` 명령행 한도를 초과할 수 있다. 특히 영어 위주의 기록이나 긴 현재 요청은 Phase 1에서 프로세스 시작 자체를 실패시킨다.  
제안: 공급자별 stdin·임시 파일 입력 지원을 실측해 프롬프트 전송 방식을 분리한다. 인수 전달만 가능한 공급자는 최종 UTF-16 명령행 길이를 실행 전에 계산해 안전한 크기로 자르고 명시적으로 경고한다.

[major] Markdown transcript만으로는 채팅 기록을 손실 없이 재개할 수 없다  
위치: `SPEC.md` §4.3, §7.4, §7.6, §7.10  
문제: 사용자와 AI의 임의 출력에는 transcript의 헤딩·구분자·코드 펜스와 동일한 문자열이 들어갈 수 있지만 메시지 경계의 이스케이프 또는 기계 판독 형식이 정의되지 않았다. 따라서 D6의 SSOT와 “채팅방 저장·재개” 완료 기준을 신뢰성 있게 구현할 수 없다.  
제안: 길이 접두어가 있는 UTF-8 레코드 등 손실 없는 내부 저장 형식을 SSOT로 두고, `transcript.md`는 사람이 읽는 파생 산출물로 생성한다. 라운드 저장은 임시 파일 후 원자적 교체 또는 append 후 fsync 정책을 정의한다.

[major] Java `ProcessHandle`만으로 프로세스 트리 완전 종료를 보장하지 못한다  
위치: `SPEC.md` §6.3, §7.7, §8.4 K4  
문제: descendants 열거와 종료 사이에 새 자식이 생성되거나 자식이 부모보다 먼저 분리되면 좀비 프로세스가 남을 수 있다. K4의 “완벽 대응 가능” 판정에는 종료 확인, 재시도, 경쟁 조건 처리가 없다.  
제안: Windows Job Object 기반 실행을 사용하거나, D12를 유지한다면 트리 반복 열거·종료·대기와 `taskkill /T /F` 직접 실행을 포함한 단계적 정책을 정의한다. 완전 보장을 구현하지 못하면 완료 기준도 “best effort”로 명시해야 한다.

[major] 일반 문맥 절단 정책이 Phase 3의 증거를 제거할 수 있다  
위치: `INTENT.md` §2, `SPEC.md` §5.3, §7.9  
문제: 최근 12개 메시지 또는 약 40,000자만 남기는 정책에서는 세 모델의 1라운드 답변과 반론이 길 경우 최초 안건이나 일부 답변이 제거된다. 그러면 합의·단독 지적·미해결을 전체 증거에 대해 분류한다는 최종 목표에 도달할 수 없다.  
제안: Phase 3에는 일반 채팅과 별도의 문맥 정책을 두고 최초 안건, 모든 구조화 응답, 반론, 검증 오류를 필수 보존한다. 크기 제한은 원문 제거가 아니라 구조화 필드별 축약 또는 사용자 확인으로 처리한다.

[major] Phase 1 명령 범위가 문서 내부에서 일치하지 않는다  
위치: `SPEC.md` §5.2, §7.9, §7.10  
문제: §5.2의 MVP 목록에는 `/cancel`, `/rooms`, `/open`이 없지만 §7.9와 §7.10은 취소와 저장·재개를 Phase 1 완료 조건으로 요구한다. `/open` 없이 재개를 자동 수행할 것인지도 정의되지 않았다.  
제안: Phase 1 명령 목록을 하나로 확정하고 `/cancel`을 포함한다. 재개는 시작 시 마지막 방 자동 복원 또는 `/rooms`·`/open` 구현 중 하나를 완료 기준에 명시한다.

[major] 대상 작업 디렉터리의 결정·보존 규칙이 없다  
위치: `SPEC.md` §5.3, §7.2, §7.8  
문제: Codex의 `-C`, agy의 `--add-dir`, 프롬프트의 작업 디렉터리에 같은 workspace가 필요하지만 그것을 현재 디렉터리, 설정값, 방별 값 중 무엇으로 정하는지 없다. 잘못된 기본값은 읽기 범위와 향후 쓰기 범위를 다른 프로젝트로 향하게 할 수 있다.  
제안: 시작 옵션 `--workspace <path>`와 현재 디렉터리 기본값을 정의하고, 정규화된 경로를 방 메타데이터에 저장한다. 기존 방을 열 때 경로가 없거나 달라졌으면 실행 전에 확인하도록 한다.
