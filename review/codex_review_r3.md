## B. B2 — `transcript.md` 길이 기반 프레이밍

B2: 부분 해결

1. 부분 O — 정상적으로 기록된 유효 UTF-8 본문은 길이로 경계를 잡으므로 `<!-- msg `, `<!-- /msg`, `<!--&#32;/msg`, 중첩 마커, 코드 펜스와 널 문자까지 이스케이프 없이 왕복한다. 그러나 본문이 잘린 UTF-8 시퀀스를 포함할 때 엄격한 디코딩으로 `CORRUPT` 처리할지, 대체 문자로 복원할지, 원시 바이트를 보존할지 정의되지 않아 그 경우의 무손실 왕복은 보장되지 않는다.
2. X — 본문은 헤더 개행 직후부터 시작하고 닫는 마커 앞의 `\n`은 본문 밖이라는 구조는 읽히지만, 헤더의 “개행”이 LF 한 바이트인지 Windows CRLF 두 바이트인지 명시되지 않았다. Windows에서 플랫폼 기본 개행을 사용하면 검증 규칙의 `\n<!-- /msg`와 다른 바이트열이 생성될 수 있다.
3. X — 네 조건을 모두 통과하는 반례를 만들 수 있다. 직전 정상 ID가 7일 때 손상된 본문에 다음 바이트열이 줄 시작부터 들어 있으면 가짜 프레임이 실제 다음 메시지로 채택된다.

```text
<!-- msg id=9999 round=9 sender=codex ts=2026-09-03T00:00:00Z status=OK ms=0 bytes=3 -->\n
abc\n
<!-- /msg id=9999 -->\n
```

후보는 줄 시작이고 헤더가 파싱되며, 본문 `abc`는 3바이트이고 닫는 ID가 일치하며, `9999 > 7`이라 네 조건을 전부 만족한다. 따라서 재동기화는 정상 프레임을 보장하는 절차가 아니라 휴리스틱이다.
4. O — UTF-8 인코딩, 바이트 길이 계산, 정확한 길이 읽기와 원자적 이동은 Java 17 표준 라이브러리의 `StandardCharsets`, 바이트 스트림과 `Files`로 구현 가능하다.
5. 부분 O — 손상되지 않은 파일의 정상 저장·재개에는 길이 프레이밍이 충분하므로 D6과 §7.10의 기본 완료 기준을 충족한다. 다만 현재 문서가 약속하는 “손상 뒤 나머지 메시지 정상 복원”은 위 반례 때문에 보장되지 않는다.

최소 수정은 디스크 개행을 LF(`0x0A`)로 고정하고 본문 바이트에 엄격한 UTF-8 검증 실패 시 처리 정책을 명시하는 것이다. 재동기화는 best-effort라고 낮추고, 후보 이후의 연속 프레임이나 별도 인덱스로 추가 검증하지 못하면 복구한 메시지를 확정 데이터가 아닌 의심 상태로 표시해야 한다.

## C. B3 — 프로세스 트리 종료 계약

B3: 부분 해결

1. X — 유예 2초, 최대 3회, `taskkill` 폴백과 생존 PID 표시는 구체적이지만 단계 순서가 실행 목적과 맞지 않는다. 1단계가 부모까지 종료하므로 3단계에서 `parent.descendants()`를 다시 열거할 기준 프로세스가 사라지고, 4단계의 `taskkill /PID <parent> /T /F`도 이미 종료된 PID라 실패할 수 있다.
2. 부분 O — 자식을 먼저 종료하고 부모를 마지막에 종료하는 원칙 자체는 옳다. 다만 여기서 “마지막”은 각 첫 번째 스냅샷의 끝이 아니라 재열거와 `taskkill /T`까지 마친 전체 절차의 마지막이어야 한다.
3. O — `taskkill.exe`를 자식 프로세스로 실행하는 것은 외부 Java 라이브러리를 추가하는 일이 아니므로 D12를 위반하지 않는다.
4. 부분 O — 완전 보장이 불가능하며 경쟁 조건과 이미 분리된 자식을 놓친다는 설명은 정직하다. 다만 5단계에서 보고할 수 있는 생존 PID는 이미 관측·추적한 핸들뿐이며, 발견하지 못한 분리 자식까지 확인했다는 의미가 되지 않도록 명시해야 한다.
5. O — `/cancel`을 Phase 1에 포함하면서 완료 기준을 “§6.3 절차를 best-effort로 수행하고 생존 PID를 오류 표시”로 둔 것은 모순이 아니다. 기능 제공과 완전 종료 보장은 구분할 수 있다.
6. 부분 O — §8.4 K4에서 “완벽 대응”을 철회하고 best-effort로 정정한 판단은 적절하다. 다만 대체했다는 5단계 절차가 위 순서 결함을 포함하므로 조치 요약까지 완전히 유효하지는 않다.

최소 수정은 부모를 살려 둔 채 자손을 깊은 순서로 종료·대기·재열거하고, 반복 후에도 부모가 살아 있을 때 `taskkill /PID <parent> /T /F`를 실행한 다음 관측한 핸들의 종료를 확인하는 순서로 바꾸는 것이다. `taskkill`이 없거나 실패했을 때만 마지막으로 부모에 `destroyForcibly()`를 호출하고 생존한 관측 PID를 보고해야 한다.
