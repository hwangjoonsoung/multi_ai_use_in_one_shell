## A. E1 — 읽기 절차 4번 문구

E1: 해결

1. §7.6 「읽기 절차」 4번은 닫는 마커 검증 실패 시 메시지를 `CORRUPT`로 표시하고, 재동기화를 시도하며 복구 후보를 `SUSPECT`로 표시한다고 수정됐다.
2. §7.6 전체를 확인했다. “정상 복원한다”는 기존 보장 문장은 남아 있지 않으며, 해당 표현은 §7.6 후반에서 폐기된 약속을 인용해 부정하는 문맥으로만 나타난다.
3. 계약은 일관된다. 손상되지 않은 파일은 `bytes` 기반 프레이밍으로 무손실 왕복을 보장하고, 손상 이후 재동기화는 best-effort이며 복구분을 `SUSPECT`로 표시한다.

## B. E2 — 재동기화 조건 4 되돌림

E2: 동의

1. 실측 해석은 맞다. 직전 정상 ID가 1이고 손상으로 ID 2 프레임을 잃었다면 이후 실제 ID 3도 `last_id + 1` 조건을 만족하지 못한다. 후보를 채택하지 못하므로 `last_id`가 계속 1에 머물고, 뒤의 모든 정상 ID도 연쇄적으로 거부된다.
2. `id > last_id`로 되돌린 판단에 동의한다. 두 방식 모두 완전하지 않지만, 연속성 강제는 한 번의 손상을 이후 전량 유실로 확장하는 반면 단조 증가 조건은 오복구 가능성을 `SUSPECT`로 공개하면서 일부 복구 가능성을 유지한다. 제시된 실측에서 완화 조건이 진짜 ID 3을 복구한 것은 아니고 가짜 ID 3을 채택했지만, 문서도 이를 성공 복구가 아닌 실패 모드 비교로 기술한다.
3. 문서는 한계를 정직하게 적었다. 정확히 `last_id`보다 크고 `next_id`보다 작은 완결된 가짜 프레임은 여전히 통과하며, 어느 조건도 완전하지 않다고 명시한다.
4. 제3의 조건: 없음. 현재처럼 단일 파일의 임의 본문에서 후보 프레임과 실제 프레임이 같은 문법을 사용할 수 있으면 후보 속성만으로 양자를 항상 구분할 수 없다. 별도의 신뢰 가능한 오프셋·인증 정보는 Java 17 표준 라이브러리로 만들 수 있지만 저장 계약 자체를 바꾸는 별도 설계이지, 두 실패 모드를 없애는 추가 후보 조건은 아니다.
5. `id < room.properties.next_id`와 `next_id` 유지는 유효하다. 단조 증가 조건이 허용하는 후보 중 아직 발급되지 않은 미래 ID를 제거하는 상한으로 작동하며, 완전성을 주장하지 않는 현재 계약과도 일치한다.

수렴자 실측은 엄격 조건이 ID 누락 뒤 복구를 중단시키고 완화 조건이 오복구 가능성을 감수해 탐색을 계속한다는 차이를 보여준다. 실험이 완화 조건의 정확한 후속 메시지 복구를 입증하지는 않지만, 문서가 주장하는 것은 정확 복구 보장이 아니라 표시된 best-effort이므로 되돌림 근거로 충분하다.

## C. 최종 판정
