## A. C1 — 개행·인코딩 규격

C1: 해결

1. O — §7.6 「규칙」은 디스크 개행을 LF(`0x0A`) 한 바이트로 고정하고, 플랫폼 기본 개행과 `PrintWriter`·`println`을 금지하며 바이트 스트림에 `\n`을 직접 쓰도록 명시한다.
2. O — 읽을 때 `CodingErrorAction.REPORT`를 사용하는 strict UTF-8 디코딩, 실패 메시지의 `CORRUPT` 처리, 해당 라운드 `runs/`의 원시 바이트 보존이 정의됐다.
3. O — 헤더 뒤 LF는 프레임 구문이고, 그 직후부터 `bytes` 바이트만 본문이며, 이어지는 LF 한 바이트부터 닫는 마커라는 단일 해석이 성립한다. 본문 끝에 LF가 원래 포함돼 있으면 그 바이트는 `bytes`에 포함되고 프레임용 LF가 하나 더 이어진다.

## B. C2 — 재동기화 조건 강화와 약속 하향

C2: 미해결

1. O — 후보 ID 조건이 `id == 직전 정상 복원 id + 1`로 강화됐다.
2. O — `id < room.properties.next_id` 조건이 추가됐고, §7.6 「규칙」에 `next_id` 유지가 명시됐다.
3. X — 재동기화 설명은 복구분을 `SUSPECT`로 표시하고 best-effort라고 낮췄지만, 같은 절의 「읽기 절차」 4번은 여전히 “나머지 메시지는 정상 복원한다”라고 단정한다. 한 절 안에서 기존 보장과 하향된 보장이 동시에 존재한다.
4. O — 강화된 조건도 `last_id + 1`이고 `next_id` 미만인 완결된 가짜 프레임을 막지 못한다고 명시해, 3라운드 반례가 남는다는 사실을 정직하게 적었다.
5. O — 손상되지 않은 파일의 무손실 왕복은 길이 프레이밍이 보장하고, 손상 후 재동기화 휴리스틱과는 별개라고 구분했다.

수렴자 실측은 손상되지 않은 파일에서 여덟 본문이 바이트 단위로 동일하게 왕복한다는 주장을 뒷받침한다. 마커·가짜 완결 프레임·널·빈 본문·다중 바이트 문자·본문 CRLF가 경계를 깨지 않는다는 것도 확인 범위에 포함된다. 다만 heredoc 단계에서 이미 U+FFFD가 생겼으므로 실제 한글 입력의 보존을 증명하지 못했고, 잘린 UTF-8의 strict 디코딩 실패 처리와 손상 뒤 재동기화 경로도 이 테스트에서는 실행하지 않았다.

최소 조치는 §7.6 「읽기 절차」 4번의 “나머지 메시지는 정상 복원한다”를 “재동기화를 시도하고 복구 후보를 `SUSPECT`로 표시한다”로 교체하는 것이다.

## C. C3 — 프로세스 트리 종료 순서

C3: 해결

1. O — 최대 3회의 반복 구간은 자손만 열거·종료하며 부모를 건드리지 않는다.
2. O — 루프가 끝난 뒤 살아 있는 부모에 `taskkill /PID <parent-pid> /T /F`를 실행하고, 명령이 없거나 실패한 경우에만 `parent.destroyForcibly()`를 호출한다.
3. O — 부모를 루프 동안 유지하므로 `taskkill /T`가 호출되는 시점에 남은 트리를 부모 PID 기준으로 정리할 수 있다. 부모가 자연 종료하는 경우까지 포함한 완전 보장은 주장하지 않는다.
4. O — 생존 PID 보고가 관측·추적한 핸들에 한정되며, “생존 PID 없음”도 추적 범위 안의 결과일 뿐이라고 명시했다.
5. O — 3라운드 최소 수정인 자손 반복 종료 → 부모가 살아 있을 때 `taskkill /T` → 실패 시 부모 강제 종료 → 관측 핸들 확인 순서와 실제 반영 내용이 일치한다.

## D. 최종 판정

CONDITIONAL — C1과 C3는 완전히 착지했다. C2의 강화된 본문도 타당하지만 같은 절에 남은 기존 “정상 복원” 보장 문장 하나를 하향된 약속과 일치시키기 전까지는 문서가 단일 계약을 제공하지 않는다.
