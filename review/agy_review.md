## A. 의도 확인

이 프로젝트는 이미 구독 중인 세 AI(Claude, Codex, Gemini/agy)의 CLI 인증을 그대로 활용하여 추가 API 과금 없이, 단일 CLI 채팅방 환경에서 세 모델을 독립적으로 병렬 호출하는 것을 출발점으로 삼는다. 핵심 목표는 단순한 3자 다중 호출이나 역할 고정형 파이프라인이 아니라, 혼자 판단하기 어려운 아키텍처·설계 안건을 세 모델에게 동시에 던져 각자의 독립적인 답변을 수집하고 상호 반론을 거쳐 합의·이견·미해결 과제를 좁혀내는 '구조화 수렴(Phase 3)' 과정을 자동화하는 것이다. 동일 라운드 내 상호 참조 차단을 통해 동조 편향과 환각 증폭을 차단하고, 최대 2라운드의 정제된 상호 검증을 거쳐 끝까지 좁혀지지 않은 핵심 쟁점만을 사용자에게 최종 결정하도록 올리는 것을 결승선으로 정의한다.

**문서를 읽고도 끝까지 모호했던 것**:
1. **Phase 3 수렴(Consolidation)의 실행 주체 및 파이프라인 구조**: 세 모델의 1라운드 답변을 대조하여 [합의 / 이견 / 단독 지적 / 미해결]로 분류하는 '수렴자(Consolidator)' 역할을 세 AI 중 특정 모델이 전담하는지, 외부 규칙 기반 엔진인지, 혹은 제4의 프롬프트 호출인지 문서 본문에 구체적 명시가 없다.
2. **라운드 종료 및 조기 수렴 판단의 기계적 조건**: 1라운드에서 세 모델이 완전 합의에 도달했을 때 즉시 수렴을 종료하는지, 혹은 이견의 경중과 상관없이 무조건 2라운드 반론을 거치는지에 대한 수렴 완료 판정 트리거가 모호하다.
3. **워크스페이스 파일 컨텍스트의 주입 및 차단 경계**: 각 CLI가 작업 디렉터리를 참조할 때 대규모 프로젝트의 무관한 파일(예: `.git`, `node_modules`, 바이너리)로 인해 컨텍스트 윈도우가 급격히 소모되는 것을 방지하는 구체적 필터링 기준이 정의되어 있지 않다.

**문서가 당연하다고 전제하지만 실제로는 적혀 있지 않은 것**:
1. **각 공급자 CLI의 사용량 쿼터 및 레이트 리밋(Rate Limit) 고갈 대응**: 구독 인증을 사용하여 추가 비용은 발생하지 않으나, 각 구독 계정의 세션당 쿼터나 시간당 호출 제한이 존재한다. 한 모델이 쿼터 초과 오류를 반환했을 때의 재시도 정책이나 대체 라우팅 규약이 없다.
2. **세 모델 간 응답 대기 시간의 현격한 편차 처리**: Flash 계열(수 초)과 고추론/Thinking 계열(수 분) 간의 실행 시간 격차가 매우 큰 환경에서, 긴 대기 시간 동안 사용자가 UI 상에서 취할 수 있는 인터랙션 허용 범위가 명시되어 있지 않다.
3. **비대화형 모드에서 워크스페이스 외부 파일 읽기 격리 수준**: 읽기 전용 모드(`read-only`, `plan`)가 워크스페이스 내 쓰기만 차단하는지, 시스템 전역 환경변수나 민감 파일(`~/.ssh`, `~/.aws` 등)의 읽기까지 차단하는지에 대한 공급자별 읽기 보안 경계가 동일한 것으로 암묵적 전제되어 있다.

## B. 미해결 쟁점 Q1~Q6 판정

Q1: 동의
근거: Java 17 표준 라이브러리 환경에서 외부 의존성 없이 JSON 파싱을 자체 구현하는 것은 이스케이프 문자 및 개행 처리에서 심각한 결함을 유발하기 쉽다. MVP의 목적은 3자 대화방의 기본 런타임과 병렬 호출 흐름을 검증하는 것이므로 `--output-format text`로 표준출력을 단순 캡처하는 것이 가장 견고하며, 구조화 스키마 파싱이 필수적인 Phase 3 전까지 불필요한 의존성 갈등(`D12`)을 원천 차단할 수 있다.

Q2: 동의
근거: 타임아웃 강제를 외부 CLI 옵션에 일임하면 공급자별 지원 여부(Codex/Claude 미지원)나 행(Hang) 상태로 인해 오케스트레이터 프로세스가 영구 블로킹될 위험이 있다. Java 9+ `ProcessHandle` API를 통해 Java 계층에서 `Process.waitFor` 및 자식 프로세스 트리의 강제 종료(`destroyForcibly`)로 통제 주체를 일원화하고, CLI 자체 타임아웃 옵션은 내부 정리용 보조 안전장치로 두는 계층형 설계가 안정적이다.

Q3: 동의
근거: 3자 독립 교차검증의 핵심 전제는 동일한 문맥과 중립적 출발선에서의 비판적 평가다. Claude가 전역 `~/.claude/CLAUDE.md`, 프로젝트 지침, 로컬 MCP 서버를 상속받아 실행되면 다른 두 모델과 출발 조건이 달라져 은닉 프롬프트가 주입되는 것과 같으므로, `--restricted` 플래그로 외부 환경 오염을 엄격히 차단해야 한다.

Q4: 조건부 동의
근거: 권장안은 결정을 사용자에게 위임하고 있어 구체적인 실행 기준이 여전히 비어 있다. 설계 문서와 구현 소스 코드가 서로 다른 위치나 형상 관리 상태로 분리되면 문서-구현 간의 불일치가 지속적으로 발생하게 된다.
대안: 현재 작업 디렉터리(`C:\Users\HJS\Desktop\multi_ai`) 자체에서 `git init`을 수행하여 저장소 루트로 확정하고, `SPEC.md` §7.1의 프로젝트 구조(`src/`, `scripts/` 등)를 현재 루트 바로 아래에 배치하여 설계 문서와 Java 코드를 단일 Git 저장소에서 일원화해 관리한다.

Q5: 조건부 동의
근거: `--restricted` 플래그는 로컬 설정 파일 로딩을 차단하지만, 부모 프로세스로부터 상속되는 환경변수(예: `CLAUDECODE` 세션 식별자)까지 완전히 격리하지는 못한다. 단순히 `/status`에서 경고를 띄우는 것만으로는 Claude 세션 내부에서 실행 시 발생하는 환경변수 간섭을 방지할 수 없다.
대안: `/status` 경고 표시와 병행하여, `ProcessLauncher`가 자식 프로세스를 기동할 때 프로세스 환경변수 맵에서 Claude Code 세션 식별 및 추적 관련 환경변수를 명시적으로 제거(Clean Environment)한 후 `claude -p`를 기동하도록 강제한다.

Q6: 동의
근거: 3자 교차검증의 파트너인 Claude(Thinking)와 Codex(reasoning effort="high")에 대등하게 대응하기 위해서는 Gemini 역시 심층 논리 분석이 가능한 고추론 모델이어야 한다. Flash 계열은 빠른 응답에는 유리하지만 미묘한 아키텍처 결함을 짚어내기에는 추론 깊이가 부족할 수 있으므로, 고추론 등급인 `gemini-3.1-pro-high`를 기본값으로 채택하고 `config.properties`를 통해 유연하게 변경할 수 있도록 한 권장안이 `INTENT.md` §2의 목적에 가장 부합한다.

## C. 새로 발견한 문제

[critical] Windows 명령행 길이 한계(32KB)와 대화 문맥 패킹(40,000자) 충돌로 인한 프로세스 기동 불가
위치: `SPEC.md` §5.3, §6.3, §7.2
문제: §5.3은 대화 이력을 최대 12개 또는 약 40,000자까지 패킹하여 전달하도록 규정하고, §6.3/§7.2는 이를 `ProcessBuilder`의 명령행 인자(`-p "<prompt>"`)로 넘긴다. 그러나 Windows Win32 API `CreateProcessW`의 전체 커맨드라인 길이 한계는 32,767자(32KB)이며, `cmd.exe` 경유 시에는 8,191자다. 대화가 5~6턴만 누적되어도 32KB를 초과하여 `CreateProcess error=206`(파일 이름이나 확장명이 너무 깁니다) 예외가 발생하며 프로세스 생성이 원천 실패한다. 반면 §6.3에서 stdin은 시작 즉시 닫도록 규정되어 있어 프롬프트를 주입할 경로가 완전히 차단된다.
제안: 프롬프트를 명령행 인수로 넘기지 말고, 프로세스 기동 직후 stdin 파이프에 UTF-8 문자열을 주입하고 `flush()` 후 스트림을 `close()`하는 방식으로 전환해야 한다. 아울러 비상시를 대비해 컨텍스트 패킹 상한을 16,000자 수준으로 안전하게 제한해야 한다.

[critical] Claude의 CLI 레벨 JSON 스키마 강제 수단 부재 및 수렴자(Consolidator) 실행 아키텍처 결손
위치: `SPEC.md` §1.5, §7.2, §7.9 (Phase 3)
문제: Phase 3의 구조화 수렴은 세 AI의 응답을 동일한 JSON 스키마로 강제하는 것을 전제로 한다. 그러나 §1.5 실측표에서 확인되듯 Codex(`--output-schema`)와 agy(`--json-schema`)와 달리 Claude CLI는 스키마 강제 플래그가 전무하며, `--output-format json`은 단순 텍스트 래퍼에 불과하다. 또한 §7.3~§7.5는 3자를 동일한 대화 참여자(`AiProvider`)로만 정의했을 뿐, 수집된 3자의 답변을 대조·분류하는 '수렴자(Consolidator)' 프로세스를 누가 어떤 프로필로 실행하는지에 대한 아키텍처가 결여되어 있다.
제안: Claude 어댑터에는 프롬프트 레벨의 스키마 강제(Few-shot) 및 스키마 검증 실패 시 1회 재질의(Retry) 로직을 필수 탑재하도록 명시해야 한다. 또한 세 검토자와 분리된 수렴 전용 실행 계약(`ConsolidationEngine` 또는 전용 호출 단계)을 §7에 선제 정의해야 한다.

[major] 대화 문맥의 단일 선형 모델과 2라운드 교차 반론(Rebuttal) 컨텍스트 분기 간의 구조적 불일치
위치: `SPEC.md` §5.3, §7.1 (`PromptContextBuilder`), §7.4, `INTENT.md` §2, §5
문제: `INTENT.md` §2와 §5의 교차 검증은 "1라운드: 상호 비공개 독립 답변" -> "대조 및 쟁점 분류" -> "2라운드: 상대 반박을 첨부하여 재질의"의 상태 머신을 요구한다. 그러나 §5.3 및 §7.1, §7.4의 설계는 단순히 이전 메시지를 시간순으로 덧붙이는 단일 선형 채팅 기록(Linear Chat Transcript) 모델로 고정되어 있다. 이 구조로는 2라운드 반론 시 특정 AI의 반박 내용만을 발췌하여 상대 AI에게 주입하는 비대칭 문맥을 생성할 수 없으며, 모든 참여자에게 전체 로그가 누적 노출되어 독립 평가가 무너진다.
제안: `PromptContextBuilder`를 단순 누적형이 아닌, 라운드 상태(`INDEPENDENT_ROUND_1`, `REBUTTAL_ROUND_2`, `CONSOLIDATION`)에 따라 각 AI에 주입할 컨텍스트를 다르게 조립할 수 있는 라운드 인식형(Round-aware) 문맥 빌더로 확장해야 한다.

[major] Codex의 `%ComSpec%` (`codex.cmd`) 경유 실행 시 특수·메타문자 해석 왜곡 및 셸 인젝션 위험
위치: `SPEC.md` §6.3 (공급자별 실행 파일 탐색 우선순위)
문제: §6.3은 네이티브 `codex.exe` 탐색 실패 시 ②순위로 `codex.cmd`를 `%ComSpec% /d /s /c`로 실행하도록 규정한다. Windows `cmd.exe`는 인자에 포함된 `&`, `|`, `<`, `>`, `^`, `%` 등의 셸 메타문자를 해석한다. 만약 프롬프트나 대화 이력에 프로그래밍 소스 코드(예: `&&`, `<vector>`, `%VAR%`)가 포함되어 있으면 명령어가 의도치 않게 분할 실행되거나 구문 오류로 크래시된다.
제안: `codex.cmd`를 셸로 직접 실행하지 말고, 스크립트 내용을 파싱하여 내부에서 실제로 호출하는 `node.exe` 및 `codex.js`의 경로를 추출한 뒤 `ProcessBuilder`가 `node.exe`를 직접 실행하도록 변경하여 `%ComSpec%` 경유를 완전히 배제해야 한다.

[major] Codex 임시 출력 파일(`-o`)의 `read-only` 샌드박스 경계 충돌 및 파일 누수 위험
위치: `SPEC.md` §7.2 (Codex 프로필), §7.6
문제: Codex는 `-s read-only` 모드로 실행되는데, §7.2는 `-o <temporary-output-file>`로 최종 출력을 파일에 기록하도록 지정한다. 만약 이 임시 파일이 현재 워크스페이스 내부에 생성되면 Codex의 샌드박스 정책에 의해 쓰기가 차단되어 실행이 실패한다. 또한 취소(`/cancel`)나 비정상 종료 시 해당 임시 파일이 디스크에 방치되거나, 파일이 불완전하게 기록되었을 때 `NoSuchFileException`이 발생하여 원본 stderr조차 확인하지 못할 수 있다.
제안: 임시 출력 파일의 위치를 워크스페이스 외부인 `%USERPROFILE%\.multi-ai-cli\temp\`로 명시 격리하고, `CodexCliAdapter` 내부에 `try-finally` 기반의 파일 회수 및 정리 로직을 의무화해야 한다. 파일 부재 시에는 stdout/stderr 스트림으로 fallback하도록 예외 처리를 보강해야 한다.

[minor] Markdown 직렬화(`transcript.md`)의 역파싱 불가로 인한 채팅방 재개(`/open`) 데이터 무결성 훼손
위치: `SPEC.md` §5.2, §7.6 (저장 규약), §7.10
문제: §7.6은 MVP에서 외부 라이브러리 없이 Java 표준 라이브러리만 사용하기 위해 대화 기록을 `transcript.md` 단일 파일로 저장한다. 그러나 AI의 응답 본문 내부에는 임의의 마크다운 헤딩, 코드 블록, 발화자 형식 문자열이 자유롭게 포함될 수 있다. 엄격한 구조화 메타데이터 없이 단순 마크다운으로 저장하면, `/open`으로 대화 기록을 다시 읽어 `ChatMessage` 객체로 역직렬화할 때 메시지 경계가 훼손된다.
제안: `transcript.md` 외에 역직렬화 전용으로 Java 표준 `java.util.Properties` 형식을 응용한 인덱스 파일(`messages.properties`)을 병행 저장하거나, 메시지 간 경계 구분을 위한 명확한 HTML 주석 태그(예: `<!-- msg:start id=... sender=... -->`)를 규격화해야 한다.

[minor] Windows 콘솔 기본 코드페이지(CP949)로 인한 한글 및 발화자 UI 렌더링 깨짐
위치: `SPEC.md` §5.1, §6.3, §7.1
문제: §6.3은 Java 프로세스의 I/O 스트림 디코딩을 UTF-8로 지정했으나, Windows 기본 터미널(PowerShell/cmd)의 콘솔 출력 코드페이지가 CP949로 되어 있는 환경에서는 `ConsoleRenderer`가 `System.out`으로 출력하는 한글 텍스트 및 발화자 식별 블록이 깨질 수 있다.
제안: `scripts/run.ps1` 시작 스크립트에 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` 및 `chcp 65001` 명령을 명시하고, Java 실행 인자에 `-Dfile.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8`를 필수로 지정하도록 규약화해야 한다.
