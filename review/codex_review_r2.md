## A. 1라운드 조치 검증

R1: 부분 해결
확인: §5.3은 공통 상한을 16,000자로 낮추고 §6.3은 Claude·Codex에 stdin을 사용하도록 개정했다. 그러나 최우선 구현 지시인 §7.2는 여전히 Claude·Codex 모두 `<prompt>`를 명령행 인자로 넘기며, §5.3의 16,000자도 “최근 메시지” 상한으로 표현돼 항상 포함되는 현재 요청·메타데이터를 합친 최종 프롬프트 상한인지 불명확하다.
남은 문제: §7.2 호출 예시를 실제 전송 방식과 일치시키고, 16,000자를 최종 조립 프롬프트 전체의 상한으로 정의하면서 현재 요청 자체가 상한을 넘을 때의 거부·안내 정책을 정해야 한다.

R2: 해결
확인: §6.3의 Codex 탐색 순위에서 `.cmd`·`.ps1` 경유가 제거됐고, 네이티브 `codex.exe` 다음으로 `node.exe`와 `codex.js`를 직접 실행하도록 바뀌었다. 둘 다 찾지 못할 때 Codex를 비활성화하는 동작도 명시돼 셸 재해석 경로가 닫혔다.

R3: 부분 해결
확인: §7.6에 메시지 ID, 라운드, 발화자, 상태를 가진 HTML 주석 경계와 원자적 교체가 추가됐다. 다만 닫는 마커 문자열만 `<!--&#32;/msg`로 치환하고 읽을 때 되돌리는 방식은 원문에 이미 `<!--&#32;/msg`가 있으면 이를 `<!-- /msg`로 바꾸므로 가역적이지 않고, 본문 속 여는 마커도 이스케이프하지 않는다.
남은 문제: 임의 본문에 대해 일대일 복원이 가능한 길이 기반 프레이밍이나 충돌 없는 인코딩으로 바꿔야 D6의 SSOT 조건을 만족한다.

R4: 부분 해결
확인: 신설된 §7.5-1이 수렴자 선택, 종료 조건, 실패·재시도 처리를 정의해 실행 주체 부재는 해결했다. 그러나 기본 방식이 참여자 한 명을 수렴자로 빼고 검토자를 2명으로 줄이므로, 세 AI가 독립적으로 답한다는 `INTENT.md` §1·§2의 기본 흐름과 일치하지 않는다.
남은 문제: 세 참여자의 1라운드 검토를 먼저 모두 받은 뒤 별도 호출로 분류할지, 2인 검토를 허용하는 별도 모드로 명시할지 Phase 3 전에 정해야 한다.

R5: 미해결
확인: §6.3과 §7.7은 여전히 “프로세스 트리 종료”만 요구하고 구체적인 종료·확인 절차가 없으며, §8.4 K4도 `descendants()`와 `destroyForcibly()`만으로 “완벽 대응”한다고 유지한다. Java 17 표준 API는 현재 관측된 자식 핸들에 신호를 보낼 수 있지만 프로세스 생성과 열거를 원자적으로 묶거나 이후 생성·분리되는 자식을 컨테이너에 가둘 수 없다.
남은 문제: 표준 Java만 유지한다면 자식부터 종료, 부모 종료, 유예 대기, 재열거, 생존 PID 보고를 포함한 best-effort 계약으로 낮춰야 한다. `taskkill /T /F` 호출은 Java 라이브러리를 추가하지 않으므로 D12를 위반하지 않지만 이미 분리된 자식까지 보장하지는 않으며, 완전 보장이 필요하면 Windows Job Object가 필요하나 Java 17 표준 API에 노출되지 않아 JNA나 네이티브 헬퍼 도입 결정을 별도로 해야 한다.

R6: 부분 해결
확인: §5.3은 Phase 3에서 최초 안건·모든 구조화 응답·반론을 필수 보존한다고 명시했다. 그러나 참조하라는 §7.9에는 여전히 일반적인 단계 목록만 있고, 보존 우선순위·크기 초과·누락 시 실패 정책은 정의되지 않았다.
남은 문제: Phase 3 착수 전 별도 문맥 정책의 입력 집합과 상한 초과 처리를 실행 가능한 계약으로 내려야 한다.

R7: 해결
확인: §5.2의 Phase 1 명령에 `/cancel`, `/rooms`, `/open`이 추가됐고, 재개는 `/rooms` 조회 후 `/open <방 ID>`로 수행하며 자동 복원하지 않는다고 확정했다. §7.9·§7.10의 취소·재개 완료 기준과 일치한다.

R8: 해결
확인: D18과 §7.8이 `--workspace`, 기존 방 메타데이터, 시작 현재 디렉터리의 우선순위를 정의했다. 절대 경로 정규화, 방별 고정, 공급자 간 동일 경로 전달, 경로 변경 확인 및 `/status` 표시까지 포함돼 있다.

R9: 부분 해결
확인: §7.5-1에 독립 검토·반론·수렴 단계의 종료 조건은 생겼지만, §7.1의 `PromptContextBuilder`와 §7.4의 조립 순서는 여전히 단일 계약이다. 각 상태에서 누구의 어느 메시지를 포함·제외하는지와 검토자별 비대칭 반론 문맥을 만드는 입력 계약이 없다.
남은 문제: Phase 3 전에 라운드 상태와 대상 참여자를 입력으로 받는 문맥 정책을 정의해야 한다.

R10: 해결
확인: §7.2의 Codex `-o`가 `%USERPROFILE%\.multi-ai-cli\temp\<run-id>.md`로 지정됐고, §7.6은 `try-finally` 정리와 파일 누락·불완전 시 stdout·stderr 폴백을 규정한다. 원래 충돌 가능성은 미검증이지만 채택된 조치로 워크스페이스 read-only 정책과 임시 출력 위치가 분리됐다.

R11: 해결
확인: §6.3은 `run.ps1`에서 콘솔 코드페이지와 `Console.OutputEncoding`을 UTF-8로 맞추고 Java 출력 인코딩도 지정한다. 완료 확인도 저장 파일뿐 아니라 실제 콘솔 화면의 한글 왕복을 포함하도록 보강됐다.

## B. 상대 단독 지적에 대한 입장

R9: 동의
근거: 1라운드는 다른 참여자의 같은 라운드 답을 제외해야 하지만, 2라운드는 해당 쟁점과 상대 반론을 대상별로 다르게 넣어야 하고 수렴 단계는 모든 유효 응답을 받아야 한다. §7.5-1의 상태 설명만으로는 `PromptContextBuilder`가 이 차이를 구현할 입력 계약이 부족하다.

R10: 부분 동의
근거: Codex `-o`가 실제로 read-only 샌드박스에 막힌다는 원래 주장은 실측되지 않았으므로 결함으로 단정할 근거는 부족하다. 다만 임시 출력을 애플리케이션 전용 디렉터리로 격리하고 정리·폴백을 정의한 조치는 비용이 낮고 워크스페이스 오염을 막으므로 유지할 가치가 있다.

R11: 동의
근거: 자식 프로세스 스트림을 UTF-8로 디코딩하는 것과 Windows 콘솔이 그 문자열을 올바르게 렌더링하는 것은 별개다. §6.3의 코드페이지·Java 출력 인코딩 설정과 화면 스모크 테스트는 Phase 1의 한글 완료 기준에 직접 필요하다.

## C. 남은 blocker

[blocker] Phase 1 공급자 호출 프로필이 확정 결정과 충돌한다
위치: `SPEC.md` §6.3, §7.0 D12·D16, §7.2, §7.7
왜 막는가: §7.2대로 구현하면 Claude·agy가 여전히 JSON을 출력해 MVP의 무외부 JSON 파서 결정과 충돌하고, agy는 10분에 자체 종료돼 Java 600초보다 긴 660초 보조 타임아웃 결정도 무효가 된다. Claude·Codex의 `<prompt>` 인자 표기도 §6.3의 stdin 전송 규칙과 반대여서 구현자가 어느 쪽을 따라야 할지 결정할 수 없다.
최소 조치: Phase 1 읽기 전용 프로필을 Claude `-p`+stdin+text, Codex `exec -`+stdin, agy `-p <prompt>`+text+`--print-timeout 11m`으로 명시하고, 16,000자가 최종 조립 프롬프트 전체 상한임을 적는다.

[blocker] transcript 경계 이스케이프가 임의 원문을 보존하지 못한다
위치: `SPEC.md` §7.6
왜 막는가: 현재 규칙은 원문 `<!--&#32;/msg`를 재개 시 다른 문자열로 바꾸고 본문 속 여는 마커 충돌도 처리하지 못한다. 이 상태로 구현하면 Phase 1 완료 조건인 저장·재개가 특정 정상 메시지를 손상시키며 D6의 SSOT가 성립하지 않는다.
최소 조치: 메시지 본문의 UTF-8 바이트 길이를 헤더에 기록하고 정확히 그 길이만 읽는 프레이밍처럼 본문 내용과 충돌하지 않는 가역 규격으로 교체한다.

[blocker] `/cancel`의 보장 수준과 종료 절차가 결정되지 않았다
위치: `SPEC.md` §6.3, §7.7, §8.4 K4
왜 막는가: `/cancel`은 Phase 1 명령과 완료 기준인데 현재 문서는 표준 Java로 완전 종료가 가능하다는 성립하지 않는 전제만 둔다. 구현자가 단일 `descendants()` 스냅샷만 종료하면 취소 후 자식 프로세스가 남아 다음 실행과 앱 종료를 방해할 수 있다.
최소 조치: Phase 1은 best-effort임을 명시하고 자식 우선 종료 → 부모 종료 → 유예 대기 → 재열거·재종료 → 생존 PID 오류 표시 절차를 규범화한다. 완전 보장을 완료 기준으로 유지하려면 D12 예외와 Windows Job Object 구현 방식을 먼저 결정한다.

[backlog] Phase 3 기본 수렴자 방식은 독립 검토자를 3명에서 2명으로 줄이므로 `INTENT.md`의 기본 흐름과 맞춰야 한다.

[backlog] R6·R9의 라운드별 문맥 보존·조립 계약은 Phase 3 착수 전에 구체화해야 한다.

[backlog] §9.2에서 채택한 Claude 중첩 실행의 비차단 경고, PID·실행 ID 관리, 세션 환경변수 제거를 §6.3 또는 §7의 실행 계약에 내려야 한다.
