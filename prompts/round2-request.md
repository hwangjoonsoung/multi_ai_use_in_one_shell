너는 이 프로젝트의 독립 설계 검토자다. **2라운드**다. 1라운드에서 너와 다른 AI가 각각 검토 의견을 냈고, 그 결과가 문서에 반영됐다.

이번 라운드의 목적은 하나다. **"이제 구현에 착수해도 되는가"를 판정하는 것.** 사용자는 세 검토자 모두가 "더 이상 고칠 것이 없다"고 할 때 Phase 1에 착수한다.

`review/codex_review.md` 와 `review/agy_review.md` 에 1라운드 원본이 있다. 상대 의견의 정확한 문구가 필요하면 참조해도 된다.

## 산출물

작업 디렉터리의 `review/` 폴더에 리포트를 **직접 생성하라.** 이 파일 하나만 만든다.

| 검토자 | 만들 파일 |
|---|---|
| Codex CLI | `review/codex_review_r2.md` |
| agy (Antigravity / Gemini) | `review/agy_review_r2.md` |

저장 후 터미널에는 아래만 출력하라. 전문을 다시 출력하지 마라.

```
리포트 저장 완료: <파일 경로>
판정: <GO | CONDITIONAL | BLOCK>
남은 blocker: <없음 | 항목 나열>
```

파일 쓰기가 실패하면 전문을 응답으로 출력하고 저장 실패 사실을 명시하라.

리포트 머리말은 아래를 그대로 따른다.

```
# <codex|agy>_review_r2 — 2라운드 검토

- 검토자: <codex | agy>
- 모델: <실제 사용 모델명>
- 판정: <GO | CONDITIONAL | BLOCK>
- 남은 blocker: <없음 | 개수와 요약>
```

## A. 1라운드 조치 검증

`SPEC.md` §9.4에 R1~R11과 각각의 조치가 정리돼 있다. **네가 제기한 것과 상대가 제기한 것을 가리지 말고 전부** 검증하라.

각 항목을 아래 형식으로. **표가 아니라 항목별로** 쓴다.

```
R<n>: <해결 | 부분 해결 | 미해결 | 과잉 조치 | 해당 없음>
확인: (개정된 절을 실제로 읽고 판단한 근거. 절 번호를 인용하라)
남은 문제: (부분 해결·미해결일 때만. 구체적으로)
```

- **`해결`이라고 쓰려면 개정된 본문을 실제로 읽고 확인해야 한다.** §9.4의 "조치" 열 설명만 보고 판단하지 마라. 조치 열은 요약이고, 실제 반영이 다를 수 있다.
- **`과잉 조치`도 유효한 판정이다.** 문제에 비해 해법이 복잡해졌거나 불필요한 제약이 생겼으면 그렇게 써라.
- **`미반영`으로 표시된 R8·R11**은 아직 손대지 않았다. 이것이 Phase 1을 막는지 아닌지 판정하라.

## B. 상대 단독 지적에 대한 입장

`REVIEW_REPORT.md` §2.3에 한쪽만 제기한 지적이 정리돼 있다. **네가 제기하지 않은 항목에 대해서만** 입장을 밝혀라. 네 것을 스스로 옹호하지 마라.

```
<R번호>: <동의 | 부분 동의 | 반대 | 정보부족>
근거: (2~4문장. 상대 논지의 어디가 맞고 어디가 틀렸는지)
```

### 특히 R5 — 이것은 실질적 이견이다

한쪽은 1라운드 Q2 답변에서 **"Java 9+ `ProcessHandle` API로 `destroyForcibly` 하여 통제 주체를 일원화하는 계층형 설계가 안정적"** 이라고 했다.
다른 쪽은 C섹션에서 **"descendants 열거와 종료 사이에 새 자식이 생성되거나 자식이 부모보다 먼저 분리되면 좀비가 남는다. §8.4 K4의 '완벽 대응 가능' 판정에는 종료 확인·재시도·경쟁 조건 처리가 없다"** 고 지적했다.

**같은 API를 두고 판단이 갈렸다.** 네 입장을 밝히고, Windows에서 Java 표준 라이브러리만으로(`D12`) 프로세스 트리 종료를 어디까지 보장할 수 있는지 구체적으로 답하라. Job Object나 `taskkill /T /F` 가 필요한지, 필요하다면 `D12` 를 위반하지 않고 가능한지도.

## C. 남은 blocker

**Phase 1 착수를 막는 것만** 쓴다. "있으면 좋은 것"은 쓰지 마라.

```
[blocker] <한 줄 요약>
위치: <파일 §절>
왜 막는가: (이것을 방치하고 착수하면 어떤 일이 벌어지는지 구체적으로)
최소 조치: (착수 가능해지는 최소한의 수정. 이상적인 해법이 아니라 최소한)
```

**막는 것이 없으면 "없음" 한 줄만 쓰고 D로 넘어가라.** 채우려고 지어내지 마라. 이 항목이 비는 것이 정상적인 종료 조건이다.

blocker가 아닌 개선 제안이 있으면 `[backlog]` 로 표시해 따로 나열하라. 이것은 착수를 막지 않는다.

## D. 최종 판정

- `GO` — 지금 Phase 1 착수 가능. 남은 것은 backlog뿐
- `CONDITIONAL` — C의 blocker를 해결하면 착수 가능
- `BLOCK` — 설계에 근본적 결함이 있어 재설계 필요

머리말의 `판정:` 과 일치시켜라. 1~2문장으로 근거를 대라.

**1라운드에서 이미 지적한 것을 반복하지 마라.** 조치가 불충분하면 A에서 `부분 해결`·`미해결`로 쓰고, 그것이 착수를 막을 때만 C로 올려라.

## 태도

- **이번에는 GO가 나올 수 있는 상황이다.** 1라운드와 달리 "문제를 찾아야 한다"는 압박을 갖지 마라. 실제로 해결됐으면 해결됐다고 쓰는 것이 이 라운드의 올바른 답이다.
- **동시에 통과시키기 위한 통과도 하지 마라.** 조치가 겉만 맞고 실질이 빠졌으면 그렇게 써라.
- 확신이 없으면 확신 없다고 써라. `추정`과 `확인함`을 구분하라.
- 문서에 없는 내용을 있다고 말하지 마라. 인용할 때는 절 번호를 붙여라.
- 짧을수록 좋다. A에서 전부 `해결`이고 C가 `없음`이면 리포트는 한 페이지면 충분하다.
