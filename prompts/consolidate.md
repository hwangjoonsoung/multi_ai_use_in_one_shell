# 수렴 절차 — 두 리뷰를 하나의 검토 보고서로

`codex_review.md` 와 `agy_review.md` 를 받은 뒤 실행한다. 산출물은 **`REVIEW_REPORT.md`** 하나다.

> **이 절차는 Phase 3의 수동 예행연습이다.**
> `SPEC.md` §7.9 Phase 3은 "`REPORT.md` 생성"이라고만 적혀 있고 형식이 정의돼 있지 않다. 여기서 손으로 만든 `REVIEW_REPORT.md` 가 **Phase 3이 자동 생성해야 할 목표 형식**이 된다. 대충 만들면 Phase 3 스펙도 대충 나온다.

---

## ⚠ 이 파일은 codex·agy에게 보내지 않는다

**이 문서는 Claude 세션에서 사람이 요청하는 절차다.** CLI로 던지는 프롬프트가 아니다.

| 파일 | 받는 쪽 | 전달 방법 |
|---|---|---|
| `review-request.md` | codex, agy | CLI 명령 (`codex exec` / `agy -p`) |
| `rebuttal.md` | codex, agy | CLI 명령 (2라운드) |
| **`consolidate.md`** | **Claude** | **대화창에 말로 요청** |

### 왜 수렴은 codex·agy가 하면 안 되는가

**자기 답안을 자기가 채점하게 되기 때문이다.** codex에게 "codex 의견과 agy 의견을 합의/이견으로 분류해줘"라고 시키면 자기 쪽에 유리하게 분류할 유인이 생긴다. 그래서 검토자(codex·agy)와 수렴자(Claude)를 분리한다.

이 프로젝트 문서 자체가 그 방식으로 만들어졌다 — codex 초안, agy 실측 검증, Claude 교차 확인.

수렴자는 **판정하지 않는다.** 두 의견을 분류하고 쟁점을 좁혀서 사용자 앞에 놓는 것까지가 역할이다. 어느 쪽이 옳은지 단정하려 들면 3자 구도의 의미가 사라진다.

## 실행

`codex_review.md` 와 `agy_review.md` 가 준비된 상태에서, **Claude 대화창에 이렇게 친다.**

> consolidate.md 대로 수렴해줘

터미널 명령이 아니다. 그냥 채팅으로 말하면 된다.

## 분류 규칙

두 리뷰의 각 항목을 아래 넷 중 하나로 배정한다. 애매하면 더 무거운 쪽으로 보낸다.

| 분류 | 조건 | 처리 |
|---|---|---|
| **합의** | 양쪽이 같은 쟁점을 제기하고 방향이 일치 | 그대로 반영 |
| **이견** | 같은 쟁점에 판단이 상충 | 2라운드 대상 |
| **단독 지적** | 한쪽만 제기 | `critical`/`major` 면 2라운드 대상, `minor` 면 기록만 |
| **미해결** | `정보부족` 표시 항목 + 2라운드 후에도 안 좁혀진 이견 | **사용자 결정 요청** |

### 2라운드 조건

**이견** 또는 **critical·major 단독 지적**이 있을 때만 실행한다. `prompts/rebuttal.md` 를 쓴다. **최대 2라운드까지만.** 그 이상 반복하지 않는다.

### 판정 충돌

머리말 `판정:` 이 갈리면(예: codex `GO`, agy `BLOCK`) 그 자체를 **최우선 이견**으로 올린다. 평균 내지 마라.

## 규칙

1. **원문을 인용하라.** "codex가 우려를 표했다"가 아니라 실제 문장을 따온다. 요약하면서 뉘앙스를 바꾸면 수렴이 아니라 창작이다.
2. **기각한 지적도 남겨라.** §3.4에 이유와 함께 적는다. 조용히 빠뜨리면 나중에 같은 지적이 다시 올라온다.
3. **양쪽이 놓친 것은 §3에 넣지 마라.** 수렴자가 새로 발견한 것은 별도로 표시한다. 검토자 의견과 섞으면 출처를 알 수 없게 된다.
4. **§4가 비어 있으면 검토가 부실했다는 신호다.** 6개 쟁점과 두 검토자에서 결정할 게 하나도 안 나오는 건 정상이 아니다. 그럴 땐 두 리포트가 실제로 서로 다른 말을 했는지 다시 본다.
5. **터미널에는 §0 판정 요약과 §4 사용자 결정 항목만 출력한다.** 전문은 파일 경로만 안내한다.
